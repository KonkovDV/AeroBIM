**Следствие 1.1.b.** Архитектурную дисциплину «в промпт попадают только структурированные

(iii) стоимость;

Ссылка на лимит вендора как на обоснование — ошибка: обоснование, привязанное к

**Следствие 1.1.c — важнейшее.** `Qwen3.6-35B-A3B` принимает изображения. Сценарий 5.3

приоритет работ: строка 2 матрицы ТЗ («Сканированные 2D / OCR», статус `PARTIAL`, риск HIGH)
и строка 19 («Неэффективное использование пространства», статус `MISSING`) становятся
достижимыми в текущем окне.

### 1.2. Жизненный цикл модели — контракт версионирования

`DOC`: URI однозначно определяет семейство и версию. Модель сохраняет URI до вывода из
эксплуатации. При значительных изменениях публикуется **новая** версия с **новым** URI.
Автоматическое переключение между версиями не предусмотрено. После окончания поддержки
запросы по устаревшему URI возвращают `400 Bad Request`. Для YandexGPT Pro 5 / 5.1 алиасы
`/latest` и `/rc` сохраняются, но вендор рекомендует явные URI.

**Следствие 1.2.a.** Это сильнее, чем предполагалось при проектировании
`AEROBIM_LLM_MODEL_REVISION`. Вендор контрактно гарантирует отсутствие тихой подмены версии.
URI **есть** пин версии.

**Следствие 1.2.b.** Гарантируется стабильность *идентификатора версии*, а не
*инвариантность функции*. Формально: пусть `M(u,t)` — функция, реализуемая моделью по URI `u`
в момент `t`. Контракт вендора утверждает, что «значительные» изменения влекут смену `u`.
Он не утверждает `M(u,t₁) ≡ M(u,t₂)`. Порог «значительности» вендором не определён —
это `UNKNOWN`.

**Следствие 1.2.c.** Алиасы `/latest` и `/rc` должны быть **запрещены конфигурацией**.
Это односимвольная проверка, дающая наибольший прирост воспроизводимости на единицу усилия.

**Следствие 1.2.d — операционный риск.** Вывод модели из эксплуатации приводит к `400` на
всех вызовах. В текущем адаптере это отобразится в `status="failed"`. Необходимо жёстко
гарантировать, что `failed` в advisory-контуре **никогда** не порождает capability `FAILED`
(которая по README роняет `summary.passed=false`). Иначе решение о ретайрменте, принятое
вендором, обваливает вердикты по всему парку установок. См. дефект D-3 в §7.

### 1.3. Квоты и лимиты

`DOC`, страница «Квоты и лимиты в Yandex AI Studio»:

| Ограничение | Значение | Тип |
|---|---|---|
| Одновременные генерации, синхронный режим | **10** (подтверждено для грантового контура) | квота на облако (изменяема) |
| Асинхронный режим — запрос | 10 / с, 5 000 / ч | квота |
| Асинхронный режим — получение ответа | 50 / с | квота |
| Пакетный режим — запуски | 10 / ч, 100 / сут | квота |
| Одновременные выделенные инстансы | 1 | квота |
| Хранение результатов асинхронных запросов | 3 суток | **лимит (неизменяем)** |

Квоты повышаются обращением в поддержку; лимиты — нет.

**Следствие 1.3.a.** «10 одновременных генераций» — квота **на облако**, а не на процесс.
Она делится между всеми параллельными прогонами AeroBIM, CI и ручными экспериментами.
Адаптер держит `BoundedSemaphore(4)` / `AEROBIM_LLM_MAX_CONCURRENT=4` — с запасом при
двух параллельных прогонах; **не повышать** без замера доли `429`. (Дефект D-1 закрыт.)

**Следствие 1.3.b.** Хранение асинхронных результатов 3 суток — неизменяемый лимит.
Любой пакетный замер обязан забирать результаты в пределах окна, иначе артефакт утрачен
безвозвратно. Для WP-06/WP-07 это операционное требование к раннеру.

### 1.4. Базовый и выделенный инстанс

`DOC`: в базовом инстансе ресурсы делятся между всеми пользователями Yandex Cloud,
поэтому при высокой нагрузке время работы моделей может увеличиваться. Другие пользователи
гарантированно не получают доступ к контексту переписок; даже при включённом логировании
запросы хранятся обезличенно, чувствительная информация маскируется. Для конфиденциальной
информации вендор рекомендует логирование отключать.

`DOC`: выделенный инстанс — гарантированные параметры производительности, не зависящие от
трафика других пользователей; отсутствие дополнительных квот на запросы и параллельные
генерации; тарификация по времени работы, а не по токенам.

**Следствие 1.4.a — уточнение контурной модели.** Выделенный инстанс устраняет
noisy-neighbour и квоты, но **не меняет отношения обработки данных**: оператором остаётся
тот же вендор, трафик идёт в тот же периметр. Классификационный уровень определяется
*отношением обработчика и границей egress*, а не выделенностью вычислительного ресурса.

Отсюда — корректная четырёхуровневая модель, заменяющая T1/T2 из ADR-002:

| Уровень | Реализация | Что улучшает | Допустимые классы |
|---|---|---|---|
| **C0** | Базовый инстанс AI Studio (РФ) | — | PUBLIC, INTERNAL |
| **C1** | Выделенный инстанс AI Studio (РФ) | латентность, квоты, предсказуемость SLA | PUBLIC, INTERNAL; **CONFIDENTIAL только при подписанном DPA** |
| **C2** | AI Studio on-premises в контуре заказчика | граница egress | CONFIDENTIAL, RESTRICTED |
| **C3** | Внешние облака вне РФ | — | ничего; профиль `NOT_VERIFIED` |

Ключевое утверждение: **переход C0 → C1 есть SLA-мера, а не мера управления данными.**
Это защищает от соблазна объявить «выделенный инстанс = закрытый контур» на защите.
Повышение класса до CONFIDENTIAL требует юридического инструмента (DPA), а не
инфраструктурного.

### 1.5. Логирование, аудит и правовой слой

| Факт | Статус |
|---|---|
| `x-data-logging-enabled: false` в заголовке REST отключает сохранение переданных данных | `DOC` |
| Для AI Studio (Workflows) логирование по умолчанию **включено** | `COMMUNITY` (Habr, 2026-03-31) |
| Для Translate по умолчанию данные **не** сохраняются | `DOC` |
| Получить историю запросов к моделям из логов **нельзя**; данные хранятся обезличенно и без привязки к аккаунту | `DOC` (раздел Q&A) |
| Инфраструктура Yandex Cloud защищена в соответствии со 152-ФЗ | `DOC` |
| Сертификация YandexGPT по ISO/IEC 42001 | `VENDOR` |
| `x-client-request-id` (UUID) — заголовок корреляции для поддержки | `DOC` |

**Следствие 1.5.a — самое существенное для управления данными.** Раз историю запросов из
логов вендора получить нельзя, **`audit_event` AeroBIM является единственной записью о
факте и содержании обращения к модели.** Вендор её не подтвердит и не опровергнет.
Это меняет требования к аудиту: он перестаёт быть дублирующим и становится первичным.
Отсюда обязательны: хеш промпта, хеш ответа, URI модели, факт отправки
`x-data-logging-enabled: false`, счётчики токенов, `x-client-request-id`. Без хешей нельзя
доказать даже собственную версию событий.

**Следствие 1.5.b.** Расхождение умолчаний между сервисами (Translate — не логирует,
AI Studio — логирует) означает, что отключение **обязано быть явным на каждом вызове** и
проверяться тестом. Полагаться на умолчание нельзя.

**Следствие 1.5.c.** Ни 152-ФЗ, ни ISO 42001 не являются DPA. Соответствие инфраструктуры
и сертификация системы менеджмента — предпосылки разговора со службой ИБ, но не его исход.
Запись `dpa: REQUIRED_BEFORE_CUSTOMER_CONFIDENTIAL` в `audit/llm_provider_policy.json`
сформулирована верно и должна остаться.

## 2. Формальная модель воспроизводимости

### 2.1. Постановка

Проект заявляет FAIR-воспроизводимость (`docs/REPRODUCIBILITY-2026.md`, run manifest,
reproducibility hash, `CITATION.cff`). Введение недетерминированного компонента ставит
вопрос: сохраняется ли заявление.

Разделим два свойства:

- **P₁ (внутрисессионный детерминизм):** при фиксированных `u`, промпте `p`, `temperature=0`
  повторные вызовы в один момент времени дают одинаковый выход.
- **P₂ (стабильность во времени):** `M(u,t₁)(p) = M(u,t₂)(p)` при `t₂ − t₁ = Δ`.

Текущая реализация оперирует одним флагом `reproducible`, что смешивает P₁ и P₂. Это
методологическая ошибка: свойства независимы, измеряются разными экспериментами и имеют
разные причины отказа (P₁ — батчинг, недетерминизм ядер, маршрутизация экспертов в MoE;
P₂ — обновление весов вендором под тем же URI).

**Рекомендация R-1.** Разделить на `deterministic_intrasession` и `stable_across_time`.

### 2.2. Протокол пробы

Расширение существующего `probe_llm_reproducibility`:

- Пусть `n` — число различных промптов, взятых из фикстурного корпуса, `k` — число повторов.
- **P₁:** для каждого из `n` промптов выполнить `k` вызовов подряд; доля промптов с полным
  совпадением всех `k` хешей — оценка `p̂₁`. Интервал Уилсона по той же методике, что в
  WP-07 (`compute_quality_protocol_stats`).
- **P₂:** повторить те же `n` промптов через `Δ = 14` суток; доля совпавших с исходным
  хешем — `p̂₂`, интервал Уилсона.
- Планирование `n`: при целевой полуширине 0.08 и ожидаемой `p ≈ 0.9` планировщик из WP-07
  даёт величину того же порядка, что и для корпуса адъюдикации. Использовать
  `plan_adjudication_corpus`, а не брать `n` из головы — инструмент уже написан.
- Публиковать нижнюю границу Уилсона, а не точечную оценку. Это согласовано с §5 протокола
  качества, где то же правило применено к порогу 0.60.

### 2.3. Главный вывод: воспроизводимость отчёта не зависит от детерминизма модели

Пусть `R` — отчёт AeroBIM, `V` — вердикт `summary.passed`, `A` — advisory-аннотация.

По ADR-001 `V = f(детерминированные находки)`, и `A ∉ dom(f)`. Тест
`test_llm_local_flag_does_not_change_verdict` подтверждает это эмпирически: `V` совпадает
при выключенном и включённом контуре.

Следовательно воспроизводимость `V` — свойство детерминированного ядра и **не затрагивается**
недетерминизмом модели. Аннотация `A` не переводится повторным выводом: она фиксируется
как артефакт с провенансом (хеш промпта, хеш ответа, URI модели, версия схемы, отметка
эксперта). Воспроизведение прогона означает воспроизведение `V` и **предъявление**
сохранённого `A`, а не его повторную генерацию.

**Формулировка для Claims Lock:**

> Воспроизводимость отчёта обеспечивается детерминированным ядром. Вывод языковой модели
> не является входом вердикта; он сохраняется как аннотация с провенансом и хешем и при
> повторном прогоне предъявляется, а не перевыводится.

Это утверждение защитимо, не требует детерминизма вендора и снимает зависимость
FAIR-заявки от чужой инфраструктуры. Проба P₁/P₂ остаётся — но как **измерение поведения
вендора**, а не как гейт публикации.

### 2.4. Отдельно — сценарий 5.2 (компилятор требований)

Здесь недетерминизм безвреден по другой причине. Артефактом является не выход модели, а
**прошедшее верификатор** требование IDS с подписью эксперта в журнале WP-04. Конвейер
«генератор → верификатор → человек» воспроизводим по построению: воспроизводится
верификатор и хранится принятый артефакт. Модель здесь — источник кандидатов, и её
недетерминизм влияет лишь на *эффективность* поиска, не на *валидность* результата.

Это классическая generate-and-test схема, и её корректность не зависит от свойств генератора.

| 19 | Неэффективное использование пространства | **MISSING** | **да** | Единственное оценочное требование ТЗ; допускает advisory-наблюдения на связке план-кроп + количества IFC |
| 20 | RU-замечания | VERIFIED_FIXTURE_ONLY | **да** | Прямой критерий оценивания ТЗ |
| 21 | EN-замечания | PARTIAL | **да** | То же |
| 22 | Критичность / приоритет | VERIFIED_FIXTURE_ONLY | нет | Детерминированная политика |
| 23 | Подсветка зон | VERIFIED_FIXTURE_ONLY | нет | Фронтенд |
| 24 | Редактор замечаний HITL | VERIFIED_FIXTURE_ONLY | усиливается | Черновик от модели + подтверждение эксперта |
| 25 | BCF | PARTIAL | нет | T2 CDE-импорт |
| 26 | SLA ≤30 мин | FIXTURE_ONLY | **риск** | См. §4 |

**Сводка.** Из 26 строк модель способна повлиять на 7 (№ 2, 8, 9, 19, 20, 21, 24) и
частично на № 12. Ни одна из них не входит в путь вердикта. Строка 19 — единственная,
где статус меняется с `MISSING`; строки 20–21 — прямые критерии оценивания.

**Строка 15 — граница, которую нельзя переходить.** Порог «точность выше 90%» в ТЗ отнесён
к коллизиям и несоответствиям. Это геометрия и cross-doc. Соблазн предъявить жюри «точность
ИИ» вместо «точности проверки» существует, и Claims Lock его уже блокирует. Никаких
изменений не требуется — требуется дисциплина.

## 4. Модель производительности и соблюдение SLA

ТЗ: обработка комплекта до 30 минут (1 800 с).

Обозначим: `N` — число находок, требующих формулировки; `L` — латентность одного вызова;
`C` — фактическая параллельность; `B` — доля бюджета SLA, отводимая advisory-контуру.

`T_llm = N · L / C`, требование `T_llm ≤ B · 1800`.

При `B = 0.2` (360 с), `N = 100` и оценочном `L ∈ [3, 8]` с:

| `C` | `T_llm`, с | Вывод |
|---|---|---|
| 1 (серийно) | 300–800 | **не проходит** в верхней части диапазона |
| 4 | 75–200 | проходит |
| 8 | 37–100 | проходит с запасом |
| 10 | 30–80 | упирается в квоту, делимую со всем облаком |

**Вывод 4.a.** Серийная реализация недопустима при `N ≈ 100`. Нужен ограниченный
параллелизм `C ∈ [4, 8]`, реализованный семафором и **конфигурируемый**, поскольку квота
делится с другими потребителями. Сейчас контроль отсутствует (дефект D-1).

**Вывод 4.b.** Базовый инстанс не даёт гарантий по латентности — вендор прямо предупреждает
о росте времени при высокой нагрузке. Следовательно `L` — случайная величина с неизвестным
хвостом. Для SLA-заявления нужны не средние, а **квантили** (p95), измеренные на реальных
прогонах, и жёсткий таймаут этапа. У проекта уже есть `stage timeout budgets` — их надо
связать с `AEROBIM_LLM_TIMEOUT_SECONDS` так, чтобы превышение давало `SKIPPED`, а не срыв
всего анализа.

**Вывод 4.c.** Для замеров WP-06/WP-07 корректный инструмент — **пакетный режим**
(10 запусков в час, 100 в сутки, результаты хранятся 3 суток), а не синхронный.
Он снимает вопрос квоты параллельности и удешевляет прогон. Текущий план использует
синхронный режим для всего — это перерасход и лишний риск.

**Вывод 4.d.** Выделенный инстанс (C1) устраняет неопределённость `L` и квоту
параллельности. Если демонстрация на КТ#2/КТ#3 идёт вживую, час выделенного инстанса на
время демо — оправданная трата гранта: он превращает `L` из случайной величины в
контролируемый параметр.

## 5. Экономическая модель гранта

Ценовые ориентиры (все `VENDOR` либо `COMMUNITY`; подлежат сверке с официальной страницей
тарифов до первого прогона):

| Позиция | Значение | Статус |
|---|---|---|
| Qwen3-235B | ≈ 0,5 ₽ за 1 000 токенов (≈ 500 ₽/млн) | `VENDOR` (анонс Yandex) |
| YandexGPT Lite / Pro 5.1 | ≈ 0,2 / 0,4 ₽ за 1 000 токенов | `COMMUNITY` |
| Выделенный инстанс | ≈ 1,5 ₽/мин (≈ 90 ₽/ч) | `COMMUNITY`, низкая достоверность |

### 5.1. Сценарий 5.1 — формулировки замечаний

Оценка на одно замечание: вход 1 200–2 000 токенов (находка + шаблон + схема), выход
200–400 (кап 512). Принимаем 2 000 токенов суммарно.

- Комплект со 100 находками: 200 000 токенов ≈ **100 ₽**.
- Бюджет трека 1 (16 000 ₽): ≈ **160 полных прогонов комплекта**.

Совпадает с оценкой в `YANDEX_AI_STUDIO_GRANT_KT2` (100–150). Оценка подтверждается.

### 5.2. Сценарий 5.2 — компилятор требований

Здесь сосредоточен реальный риск перерасхода. При корпусе из ~138 требований, входе ~2 000
токенов на требование, выходе ~800 и трёх итерациях repair-loop:

`138 × (2000 + 800) × 3 ≈ 1,16 млн токенов ≈ 580 ₽` за одну компиляцию нормопака.

Десять итераций разработки промпта и схемы — ≈ 5 800 ₽, то есть **треть трека 1**.
Именно поэтому потолок `max_tokens_per_run` критичен, и именно поэтому он должен быть
задан **ниже** дефолтных 500 000 на время отладки.

### 5.3. Сценарий 5.3 — VLM по фрагментам

Изображения дороже текста. Ориентировочно 2 000 токенов на кроп при 200 кропах на комплект:
≈ 460 000 токенов ≈ **230 ₽** за комплект, вдвое дороже текстового контура. Для точечного
применения к штампам, экспликациям и размерным цепочкам — приемлемо. Для сплошной обработки
всех листов — нет, и это ещё один аргумент за region-crop вместо целого листа.

### 5.4. Ключевой вывод: грант не является узким местом

Один замер по протоколу WP-07 требует `n ≈ 111` адъюдицированных элементов (полуширина
Уилсона ≤ 0,08 при `p = 0,75`). Это ≈ 222 000 токенов ≈ **111 ₽**.

Иными словами, полный цикл измерения качества стоит около одной сотой гранта.
**Узкое место — не деньги и не токены, а два эксперта-адъюдикатора и корпус заказчика.**
Это следует зафиксировать в переписке с трекером: увеличение квоты полезно, но оно не
приближает закрытие RT-001. Смешивать эти два дефицита в одной аргументации —
методологически неверно и уязвимо на защите.

## 7. Дефекты текущей реализации

Приоритет по произведению «вероятность × ущерб».

| ID | Дефект | Severity | Обоснование |
|---|---|---|---|
| **D-1** | Нет контроля параллельности и обработки `429` | **высокий** | Квота 10 делится на всё облако; при `N ≈ 100` серийный режим не проходит SLA, параллельный без семафора даст отказы |
| **D-2** | Не отправляется `x-data-logging-enabled: false` | **высокий** | Умолчание AI Studio — логирование включено; вендор сам рекомендует отключать для конфиденциальных данных; сейчас поле `data_retention` в политике не подкреплено поведением |
| **D-3** | Не доказано, что `status="failed"` не порождает capability `FAILED` | **высокий** | Ретайрмент модели вендором даёт `400` → при неверном отображении обваливает `summary.passed` по всему парку |
| **D-4** | `request_id` уходит в тело промпта, а не в `x-client-request-id` | средний | Раздувает промпт, не даёт корреляции с поддержкой, а иной записи не существует (§1.5.a) |
| **D-5** | Нет валидации формы URI; `/latest` и `/rc` не запрещены | средний | Прямо противоречит цели `AEROBIM_LLM_MODEL_REVISION`; вендор рекомендует явные URI |
| **D-6** | Флаг `reproducible` смешивает P₁ и P₂ | средний | Методологическая ошибка; делает результат пробы неинтерпретируемым |
| **D-7** | Не используется пакетный режим для корпусных замеров | низкий | Перерасход и лишняя нагрузка на квоту параллельности |

Отдельно, из предыдущего ревью и не закрыто: **allowlist применяется только в
`Settings.from_env`**, адаптер его не перепроверяет. При заявленном принципе защиты
в глубину — остаточный дефект низкой критичности.

## 10. Итоговая оценка

Доступ к Yandex AI Studio закрывает контурный разрыв, который до сих пор оставался
теоретическим: маршрут `private` перестаёт быть проектной абстракцией и получает
работающий эндпоинт в юрисдикции РФ с документированным путём в закрытый контур заказчика.

Три вывода, меняющие план:

1. **Сценарий 5.3 доступен сейчас, а не в сентябре** — модель мультимодальна, локальное
   железо не требуется. Это закрывает единственное `MISSING` в матрице возможностей.
2. **Воспроизводимость отчёта не зависит от детерминизма модели** — потому что вывод модели
   не является входом вердикта. Это снимает главное возражение против облачного контура и
   формулируется в одну фразу для Claims Lock.
3. **Грант не является узким местом** — полный цикл измерения качества стоит около процента
   от него. Дефицит — эксперты и корпус, а не токены.

Ни один из выводов не приближает Checkpoint к GO. RT-001, RT-002 и RT-003 закрываются
артефактами заказчика, и ни доступ к модели, ни её качество на это не влияют.
