# Пилот, пробный доступ и интеграция

Этот файл — отдельный сценарий, который организаторы могут переслать заказчику.
Репозиторий на GitHub **не** заменяет отчёты по трём направленным комплектам и
**не** является пробным стендом. Канал — только организаторы. Прямой почты
заказчику канала из git нет.

Checkpoint **`GO`**; `customer_go` **false**. Учебный `POST /v1/demo/seed-fixture`
на пробный контур **не** ставится.

## 1. Три отчёта по направленным проектам

По каждому из трёх слотов канала (`pack_a` / `pack_b` / `pack_c`) локально
собраны:

| Выдача | Назначение |
|---|---|
| Двухстраничная выжимка | Что прогнано, что не проверено, какие карточки смотреть |
| 6–8 карточек `--strict-evidence` | Наблюдаемое и ожидаемое; форма решения эксперта (CSV) |
| HTML / JSON / PDF / BCF ZIP | Полный машинный отчёт того же `report_id` |

Это **карта выгрузки и комплектности**, не акт «дом бракованный» и не точность
продукта. IDS в прогоне — публичный unsigned IFC2X3 presence, **не** подписанный
профиль назначающей стороны. Native RVT / NWD / DWG в отчёте стоят как отказ чтения, не как
«файл битый». AABB-clash без согласованного зазора в shortlist не входит.

Ссылки на файлы отчётов **не публикуются на GitHub**. Владелец кладёт пакет в
согласованный контур организаторов (диск / закрытая ссылка) и пишет три URL в
письмо. Пока письмо не ушло и нет письменного «получено», статус слота —
`ready_local`, не `sent`.

Как читать выжимку: [`CUSTOMER_REVIEW_PACK_RUNBOOK_2026_09.md`](CUSTOMER_REVIEW_PACK_RUNBOOK_2026_09.md).
Цепочка доставки: [`DELIVERY_INTEGRITY_2026_09.md`](DELIVERY_INTEGRITY_2026_09.md).

## 2. Пробный доступ (самостоятельная проверка на контрольных данных)

Заказчик должен сам загрузить **свои** контрольные файлы. Демо-seed из git и
шаринг экрана это **не** заменяют. Анонимный доступ запрещён. Публичное облако
как место хранения комплекта — нет.

**Основной вариант — on-prem Docker у заказчика (рекомендуем).**

1. Организаторы передают offline-bundle (образ + `INSTALL_OFFLINE.md`) либо
   клон репозитория + `docker compose -f docker-compose.production.yml`.
2. Заказчик задаёт два секрета: `AEROBIM_API_BEARER_TOKEN` (эксперт) и
   `AEROBIM_REDIS_PASSWORD`. Роль «просмотр» — отдельный токен/прокси, не
   общий anonymous.
3. `AEROBIM_ENV=production` уже выключает `POST /v1/demo/seed-fixture`.
4. Контрольные IFC/PDF монтируются **вне** `./samples` (git vertical slice —
   не три проекта канала).
5. Analyze: API `POST /v1/analyze` либо CLI
   `python -m aerobim.tools.run_channel_slot_analyze` на согласованном слоте.
6. Смотреть: HTML-отчёт, JSON, BCF-файл. Импорт BCF в их СОД в этот контур
   **не** входит (`cde_import=NOT_VERIFIED`).

**Запасной вариант — time-boxed HTTPS.** Именованные учётки эксперта и
просмотрщика на ВМ, которую указывает заказчик или организатор. Срок: 5
рабочих дней, затем отзыв токенов. Reverse-proxy с HTTPS; bind приложения
остаётся loopback. Не публичный SaaS.

Что заказчик увидит на контрольных данных в пробном доступе: тот же класс
проверки, что в трёх отчётах (IFC + IDS + комплектность; PDF — если OCR-слой
жив). Это не измерение «точность >90%» и не SLA «до 30 минут».

## 3. Формат пилота (если победа / соглашение площадки)

Срок ориентира: **30–60 календарных дней** на **одну типовую секцию** одной
ревизии. Юридическая оболочка — соглашение Партнёр↔Фонд (формы М2/M7/M9 у
оператора Фонда). Мы не сочиняем форму акта.

| Неделя | Что делаем | Что подписывает заказчик |
|---|---|---|
| 0 | Scope memo: разделы, стадия П/Р, что *не* проверяем (native CAD, решатель, полный MEP) | Scope + режим данных |
| 1 | Каноническая ревизия комплекта + черновик IDS как **данные**, не форк ядра | Должность подписанта профиля |
| 1–2 | Прогон в их контуре; выдача 10–25 карточек одному named expert (60–90 мин) | Решения: подтверждено / ложно / не решено / уже знали |
| 3–6 | Повтор после исправлений; BCF-файл в их процедуру импорта | Лог/скрин импорта, если T2 в scope |
| Финал | Методика: interim precision **0,60** на выборке **111** (62 — только мощность). Если нижняя граница Уилсона 95% < **0,50** — сужаем область, цифру не докручиваем | Акт площадки по форме Фонда |

Два независимых разметчика по 2–4 ч — условие **publishable** точности, не
условие первого пилотного прогона. LLM разметчиком не является.

Критерии брифа «точность >90%» и «пакет за ≤30 минут» в акт **не** переносим,
пока их не подтвердят или не снимут письмом. Молчание ≠ согласие.

Три числа эффекта, без которых рубли не рисуем: рабочие дни круга РД по
секции; часы ручной проверки «до»; сколько лишних кругов считают нормой.
E1–E5: [`CUSTOMER_CYCLE_ECONOMICS_ASSUMPTIONS_2026_09.md`](CUSTOMER_CYCLE_ECONOMICS_ASSUMPTIONS_2026_09.md).

RACI: [`PILOT_RACI_ONEPAGER_2026_09.md`](PILOT_RACI_ONEPAGER_2026_09.md).
Протокол измерения: [`../pilot-protocol-customer-2026.md`](../pilot-protocol-customer-2026.md).

## 4. Сценарий последующей интеграции

Интеграция **после** пилота, не вместо него. Платформу заказчика дорабатывать
не нужно.

```text
их СОД / диск
    → выгрузка IFC + PDF/A (+ IDS, если подписан)
    → AeroBIM (Docker в их контуре)
    → JSON + HTML + BCF-файл
    → импорт BCF штатным механизмом их СОД (делает их PMO)
```

1. **Обмен файлами.** Нулевой CAPEX. Нет живого коннектора 10D/Tangl.
2. **Профиль — данные.** Их IDS/ИТЗ версионируется рядом с ядром; ядро не
   форкаем под одного заказчика.
3. **Вердикт.** `summary.passed` пишет детерминированный слой. Эксперт
   подтверждает или отклоняет. Нейросеть вердикт не подписывает (ADR-001).
4. **Идентификация.** Пилот: два именованных bearer. SSO/OIDC/BFF на их IdP —
   следующий подписанный шаг; сегодня `GET /v1/auth/bff` по умолчанию **501**.
5. **Не в первой волне:** native DWG/RVT/NWD, системный MEP clash, запись в
   реестр СОД «из коробки», реестр российского ПО как статус.

## 5. Что просим подтвердить письмом

1. Режим данных по уже переданному каналу 25.08 (куда можно класть производные).
2. Порог пилота: 0,60 по этой методике **или** иной порог одной строкой.
3. Кто named expert на пакет 10–25 карточек.
4. On-prem Docker **или** ВМ под time-boxed HTTPS (куда слать образ и токены).

Checkpoint **`GO`**; `customer_go` false, пока нет независимого размеченного
корпуса, двух разметчиков, подписанного профиля и доказательства импорта в СОД.
