# Протокол измерения качества и приёмки решения задачи №7

**Адресат:** ТИМ-руководитель / куратор пилота (ГК «Самолёт», МИК)  
**Версия:** 1.0 · **Дата:** 4 августа 2026  
**Статус:** предложение критерия приёмки для **всех** участников задачи №7  
**claim_level:** protocol_only — не публикует продуктовую точность AeroBIM  
**Закрывает RT-001?** нет, пока не передан и не размечен корпус заказчика  

> **Одной фразой.** В ТЗ сказано «точность >90%», но не определено, *что* именно измерять. Этот документ закрывает дыру: предлагает единый, воспроизводимый способ измерения для любого решения на пилоте — включая AeroBIM и остальных финалистов.

## 1. Зачем нужен протокол (и почему он общий)

Раздел ТЗ «Критерии оценивания» опирается на формулировку вроде «точность >90%» и целевое время обработки комплекта. Без операционального определения любая цифра остаётся непроверяемой:

| Вопрос, который ТЗ не фиксирует | Что фиксирует этот протокол |
|---|---|
| Precision или recall? | **Оба**, раздельно; для критических ошибок — отдельный порог recall |
| На каком корпусе? | Согласованный комплект(ы) заказчика + held-out |
| Кто размечает эталон? | ≥2 независимых эксперта заказчика (двойная слепая) |
| Как снимаются разногласия? | Журнал adjudication + κ/α |
| Учитываются ли пропуски (FN)? | Обязательно |
| Агрегат или по классам? | **По классам ошибок**; макро только как сводка |
| Воспроизводим ли прогон? | Хеш комплекта, версия ПО, оборудование, cold/warm |

**Предложение:** принять этот протокол (или его согласованную редакцию) как **единый критерий приёмки пилота задачи №7** для всех участников. Тогда сравниваются не обещания, а отчёты, построенные по одним правилам.

AeroBIM не претендует в этом документе на достижение порога >90%. AeroBIM предлагает **методику**, которой порог можно честно подтвердить или опровергнуть.

## 2. Что считается «ошибкой» и как считается точность

### 2.1. Классы ошибок (операционально)

Измерение ведётся **по классам**. Смешивать классы в одну метку запрещено.

| Класс | Что это на практике | Типичное доказательство |
|---|---|---|
| Коллизии / clearance | Пересечения, недопустимые зазоры по согласованной матрице | Идентификаторы элементов модели |
| Размеры / габариты | Расхождение размера между источниками сверх допуска | Лист + значение в модели |
| Площади / ТЭП | Расхождение площади (модель ↔ чертёж / таблица) | Space / quantity + лист |
| Несогласованность разделов | ПД↔РД, ТЗ↔модель, расчёт↔документ | Пара документов + цитата / число |
| Отсутствующие элементы | Требуемый объект/свойство отсутствует | Правило существования / IDS |
| Расчётные расхождения | Число в расчёте ≠ число в документации/модели | Два источника чисел (**не** «система пересчитала правильно») |
| Прочее | Только с явной пометкой | — |

### 2.2. Четыре исхода разметки (не путать с «зелёным отчётом»)

| Исход | Смысл |
|---|---|
| **TP** | Система указала на реальную ошибку (подтверждено экспертом) |
| **FP** | Система указала ложно |
| **FN** | Ошибка есть в эталоне, система не указала |
| **Исключено / неразрешено** | Неполная исходная, спор вне порога согласия — **не** входит в публикуемую точность |

### 2.3. Формулы (без смешения)

Для каждого класса \(c\) на held-out выборке:

\[
\mathrm{Precision}_c = \frac{\mathrm{TP}_c}{\mathrm{TP}_c + \mathrm{FP}_c}, \quad
\mathrm{Recall}_c = \frac{\mathrm{TP}_c}{\mathrm{TP}_c + \mathrm{FN}_c}
\]

**Отдельно** для критических ошибок (согласованный перечень до старта):

\[
\mathrm{Recall}_{\mathrm{critical}} = \frac{\mathrm{TP}_{\mathrm{crit}}}{\mathrm{TP}_{\mathrm{crit}} + \mathrm{FN}_{\mathrm{crit}}}
\]

**Ложный пропуск (false pass) — первая строка отчёта.** Система сказала «соответствует», эталон — нарушение. Для экспертизы это опаснее ложного срабатывания. Считается отдельно от FP. Источник, почему единица наблюдения — **проект**, а не задача: Mushkani, Bérard, Koseki, [arXiv:2607.29058](https://arxiv.org/abs/2607.29058). Доверительные интервалы — кластерный бутстрэп по проектам (`aerobim.domain.eval_statistics.cluster_bootstrap_cis`), не i.i.d. биномиал по находкам.

Макро-среднее по классам допускается только как сводка и **не** заменяет отчёт по классам.

> Запрещено называть «точностью» одну цифру без указания: precision/recall, класс, корпус, n, доверительный интервал.

### 2.4. Доверительные интервалы и размер выборки

Биномиальные доли сопровождаются **интервалом Уилсона** (не «голым» процентом).  
Размер выборки планируется **до** просмотра срабатываний системы (инструмент: `compute_quality_protocol_stats`).

Ориентиры для согласования с заказчиком (пересчитать под ваши допущения):

| Цель планирования | Пример входа | Следствие |
|---|---|---|
| Показать interim precision ≥ 0.60 | ожидаемая p, полуширина CI, доверие 0.95 | требуемый n размеченных находок |
| Удержать полуширину CI ≤ 0.08 при p≈0.75 | те же параметры | n из планировщика |

**Interim-порог пилота (не ТЗ-«>90%»):** подтверждённые находки  
\(\mathrm{TP}/(\mathrm{TP}+\mathrm{FP}) \ge 0.60\) на held-out — при выполнении гейтов публикации (§5).  
Порог «>90%» из ТЗ остаётся **аспирацией**, которую можно проверить тем же протоколом после достаточного n и согласия экспертов — без подмены fixture-цифр.

## 3. Процедура эталона: двойная слепая разметка

1. **Freeze комплекта** до разметки: состав файлов, ревизии, хеши, версия проверяющего ПО.  
2. **Два независимых эксперта** заказчика размечают без доступа к меткам друг друга и без «третьего голоса» LLM.  
3. Считается согласие (Cohen’s κ / Krippendorff’s α). Стартовый ориентир для пилота: κ ≥ 0.60 (порог письменно согласовать; «0.8» не магическое число).  
4. Разногласия → заседание adjudication (третий эксперт или sponsor заказчика) → запись в журнал с итоговым вердиктом.  
5. Позиции `неразрешено` **исключаются** из публикуемой precision/recall.  
6. Held-out: часть корпуса не используется для настройки правил до финального отчёта.

Инструкция для экспертов уже существует: [`EXPERT_LABELING_INSTRUCTION_2026.md`](../pilot/EXPERT_LABELING_INSTRUCTION_2026.md).  
Шаблоны журнала: `samples/benchmarks/detection-precision/`.

## 4. Замер времени обработки комплекта

Цель «уложиться примерно в 30 минут» имеет смысл только как **измерение**, а не как лозунг.

Обязательные поля протокола замера (исполняемый контур: `measure_package_sla`, schema ≥1.3 / актуальная 1.4.0):

| Поле | Зачем |
|---|---|
| Состав комплекта (инвентарь файлов) | Сопоставимость прогонов |
| Хеш пакета | Воспроизводимость |
| Отпечаток машины / среды | Без этого SLA с чужого ноутбука бессмысленен |
| Cold / warm, итерации | Исключить «разогретый» артефакт |
| Основной гейт | **p95** cold-времени (не среднее) |
| Бюджеты стадий | Ingestion / deterministic / advisory / reporting |
| Уровень утверждения | `fixture_only` **или** `customer_measurable` — второе только на корпусе заказчика при полных полях |

Утверждение «customer SLA ≤30 мин» **отказывается** инструментом, если нет корпуса заказчика, хеша, отпечатка машины и полноты обязательных проверок. Fixture-замеры не переносятся в продуктовую презентацию.

## 5. Когда цифру можно показывать заказчику (гейт публикации)

Публикация precision/recall как показателя решения задачи №7 допускается **только** если одновременно:

1. Корпус = **заказчик** (или явно согласованный пилотный пакет заказчика), не открытый бенчмарк и не fixture.  
2. ≥ **2** независимых разметчика.  
3. Согласие κ/α не ниже письменно согласованного порога.  
4. Held-out зафиксирован.  
5. FN учтены (нет «precision без recall»).  
6. Отчёт по классам + Wilson CI; для критических — отдельный recall.  

Это соответствует кодовому гейту `PrecisionClaim` / `precision_claim_publishable_with_agreement`: без customer + adjudicators≥2 значение **не** отображается как продуктовая точность.

**Не путать уровни чисел:**

| Уровень | Пример | Что это |
|---|---|---|
| L1 open-bench | AECV `macro_extended≈0.43` | Открытый бенчмарк чертежей ≠ продукт |
| L2 fixture | extraction `macro_f1≈0.86` | Тестовый корпус репозитория ≠ продукт |
| L3 пилот / RT-001 | (пока нет) | Единственный уровень для приёмки задачи |

## 6. Критерии остановки и сужения пилота

Пилот **можно расширять**, если:

- обязательные проверки стабильно запускаются;  
- у находок есть источник и доказательство;  
- качество измерено на замороженном наборе по этому протоколу;  
- recall критических ошибок не ниже согласованного порога;  
- время измерено по §4;  
- есть сравнение с baseline ручных часов (зафиксированным **до** эффекта).

Пилот **следует остановить или сузить**, если:

- эксперты перестают доверять результатам;  
- критические ошибки пропускаются чаще порога;  
- обязательные проверки нестабильны;  
- источник находки нельзя восстановить;  
- времени/масштаба нет;  
- эффекта относительно baseline нет;  
- заказчик не может передать приложения, перечисленные в ТЗ (примеры ПД/РД, стандарты/требования, типовые ошибки, расчётные материалы) — без них **невозможно** закрыть измерение, а не «вина метода».

Неудача одного класса ошибок ≠ провал всей идеи: область сужается до классов, где порог доказан.

## 7. Что требуется от заказчика для запуска измерения

Раздел ТЗ «Приложения и источники данных» уже перечисляет состав, необходимый для измерения. Рабочая формулировка: это **состав приложений к задаче**, ожидающий передачи, а не «дыра в продукте».

| # | Нужно | Зачем |
|---|---|---|
| 1 | Определение «комплекта» + baseline часов ручной проверки | Эффект и сопоставимость |
| 2 | Каталог типовых ошибок + кто его утверждает | Классы + критичность |
| 3 | Два разметчика со стороны заказчика | κ/α и эталон |
| 4 | Утверждённые требования / нормы в машиночитаемом или согласованном виде + кто подписывает | Правила проверки |
| 5 | Куда попадают подтверждённые замечания (принимается ли BCF) | Замыкание процесса |

До передачи — допустимы только открытые/fixture прогоны с явной пометкой «не данные заказчика».

## 8. Предлагаемое решение для куратора задачи

1. Принять (или согласовать правки к) **этому протоколу** как единый способ проверки «точности» и времени для всех финалистов задачи №7.  
2. Зафиксировать interim-порог пилота (рекомендация: confirmed-finding ≥ 0.60) отдельно от аспирации ТЗ >90%.  
3. Передать приложения по §7 и назначить двух разметчиков.  
4. Провести один измерительный цикл: freeze → разметка → отчёт по классам + время → решение expand / stop / narrow.

AeroBIM готов исполнять протокол на переданном комплекте в закрытом контуре пилотного профиля и отдавать evidence-бандл с хешами и журналом разметки.

## Приложение B. Claims Lock (кратко)

Не заявляется этим документом: продуктовая точность >90%, customer SLA ≤30 мин, native DWG, MEP delivered, CDE-ready BCF, «корректность расчётов доказана».
