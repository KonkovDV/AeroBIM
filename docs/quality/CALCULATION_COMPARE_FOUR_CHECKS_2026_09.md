# Четыре проверки «заявленное vs записка»

Заказчик 25.08 сформулировал сверку РД/BIM с расчётами как **сопоставление заявленных значений**, не как независимый пересчёт. Этот файл — операционализация. Бинарный `.lir` не разбирается (`native_lir=not_implemented`). Присутствие носителей ЛИРА в unpack-дереве — локальный ценз (`.local/`), не разбор. На одном из корпусов расчётной модели нет. Один блок на эталонном корпусе неполон. Решатель ЛИРА/SCAD за скоупом MVP; это произносится жюри вслух (IUA TL-10; triage `RT-LIRA-SOLVER`).

Нормативная опора (публичная): СП 63.13330 (железобетон), СП 20.13330 (нагрузки и воздействия). Профиль приёмки назначающей стороны (RT-002b) **не** подписан; городской IDS (RT-002a) эти четыре проверки **не** заменяет.

## Операционализация

| ID | Проверка | Источник «заявлено» | Источник «записка» | Надёжность извлечения | В MVP |
|---|---|---|---|---|---|
| CC-1 | Площадь армирования \(A_s\) (недобор относительно расчёта) | КР-листы PDF (векторный текстовый слой); **не** IFC, пока `IfcReinforcingBar` отсутствует в выгрузке | Расчётная записка PDF/таблицы; текстовый протокол расчётного комплекса, если передан как текст | средняя: нужна привязка марка/ось | выборочно, по согласованному списку элементов |
| CC-2 | Класс бетона / стали | IFC `IfcMaterial.Name` (на КР выгрузке есть токены **B25 / B35**); текст КР ПЗ | Записка / спецификация материалов | высокая для бетона при совпадении строк класса; сталь — текст записки (в IFC-именах стали нет) | да, сопоставление строк **если** есть записка |
| CC-3 | Прогибы | РД поэлементно прогибы часто **не** заявляет | Записка vs предельные по СП 20 | средняя (таблицы PDF) | выборочно; это «записка vs норма», не всегда «РД vs расчёт» |
| CC-4 | Нагрузки (и площади как сопутствующее) | Сбор нагрузок Office; ТЭП ПЗ; load cases в текстовом протоколе | Записка / комбинации | высокая при машиночитаемых таблицах | да, declared-field compare |

## Вердикт к закрытию окна КТ#3 (методика, не прогноз балла)

Ожидаемый **частичный GO методики**: CC-2 и CC-4 как полный контур сопоставления при наличии записки; CC-1 и CC-3 — выборка. Это **не** «конструкции пересчитаны» и **не** точность продукта.

Условия, которые git не закрывает: соответствие ревизий ПД/РД/записки (владелец); каноничность PDF-записки vs «расчётного» Excel; передан ли армирующий результат расчёта в читаемом виде.

Локальный pre-check (не MATCH): `python -m aerobim.tools.scan_declared_calc_tokens <unpack-tree> --output .local/pack-out/sig06-token-scan.json` — байт-токены. Сжатый PDF может скрыть токен. На unpack-дереве есть shortlist Office-файлов с токенами «класс бетона» и нагрузок. Это shortlist, не CC-2 MATCH. Каноничная записка — владелец. Пофайловые счётчики shortlist в git не пишем.
