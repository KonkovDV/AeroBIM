# Текст слайдов КТ#2

Основная дека: [`aerobim_kt2.pptx`](aerobim_kt2.pptx) · [`aerobim_kt2.pdf`](aerobim_kt2.pdf). Этот файл — текст для речи и сверки формулировок. Источник цифр: [`../../docs/demo/KT2_CORPUS_SSOT_2026_08.md`](../../docs/demo/KT2_CORPUS_SSOT_2026_08.md). Формула стадии: [`../../docs/demo/KT2_JURY_FAQ_2026_08_12.md`](../../docs/demo/KT2_JURY_FAQ_2026_08_12.md).

## Слайд 1. Проблема

- AeroBIM ловит расхождения **между** файлами комплекта: площадь в ведомости против площади в IFC, отметка в ПД против отметки в РД, требование ТЗ против фактического наполнения.
- Каждый файл по отдельности открывается чисто. Дефект живёт в шве и обычно всплывает на площадке.
- Ручная сверка зависит от квалификации и времени эксперта. Полный контроль всей документации не обещаем.

## Слайд 2. Решение

- Доказательная проверка IFC-пакета перед согласованием: требование → правило → объект → доказательство.
- Эксперт остаётся ответственным. Система не подписывает переход Shared → Published.
- AeroBIM не заменяет 10D, Tangl, авторинг заказчика, СОД и эксперта: независимый слой проверки поверх существующего контура.
- Tangl проверяет модель, AeroBIM — комплект. Интеграцию с 10D не заявляем: только file/API-граница. IFC принимаем **как его выгружает ваш авторинг** — публично подтверждены Tangl + Power BI + 10D; авторинг Самолёта в открытых источниках не фиксируем. Renga — в контуре ИЖС / импортозамещения, не факт «стек = Renga».

## Слайд 3. Архитектура

- Четыре контура: загрузка → детерминированная проверка → советующий ИИ → отчёт.
- Технический флаг `summary.passed` ставят только детерминированные движки (ADR-001).
- Языковая или визуальная модель не может превратить отказ в успех.
- Молчание не считается успехом: пропуск обязательной проверки роняет комплект.

## Слайд 4. Демонстрация

- Живой прогон на учебном комплекте: `python -m aerobim.tools.run_demo_ifc_acceptance_gate`.
- Находка: GUID элемента, идентификатор правила, пара expected/observed, ссылки на evidence (HTML, JSON, BCF).
- `summary.passed=false` на учебном комплекте ожидаем: в фикстуре заложены дефекты.
- Оверлей `run_demo_vertical_slice` — только P1. Снимок HTML 11.08 и `wall-guid/report.html` в кадре не открывать.

## Слайд 5. Методика

- Методика прежде процента. Целевые цифры ТЗ — критерии заказчика, не наши замеры.
- В протоколе: TP/FP/FN, два разметчика, hidden holdout, κ/α, cold/warm, хеш пакета и версия правил.
- Без корпуса заказчика оценку продукта не публикуем. κ/α на комплекте Самолёта не измерены.
- Открытые бенчмарки — регрессия движка, не корпус «Самолёта».

## Слайд 7. Статус

Дословно, если спросят «где вы сейчас»:

> Мы на стадии доработки. Одна команда показывает находку с доказательствами на учебном комплекте. Валидация эффективности и внедрение ещё не начались. `NO_GO` сохраняется, пока нет независимого размеченного корпуса, двух разметчиков, профиля приёмки (публичные IDS экспертизы — измерение; подпись Самолёта — внедрение) и подтверждения импорта в СОД.

Четыре пункта запроса к заказчику (без них RT-001/002 OPEN; SLA и TP не мерим):

1. Согласованный комплект той же ревизии: ПД/РД + IFC + 2D/PDF + фрагмент ТЗ/EIR.
2. Подписанный профиль приёмки (IDS / rule pack + approval_ref / pack_hash).
3. Два инженера-разметчика на TP/FP.
4. Цель СОД для BCF: система и версия, куда импортировать замечание (скрин/лог импорта). Не API 10D.
