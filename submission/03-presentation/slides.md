Одна колода, язык — русский. Бинарник деки в git не кладётся: его готовит оператор 19.08 из этого текста. Источник цифр: [`../../docs/demo/KT2_CORPUS_SSOT_2026_08.md`](../../docs/demo/KT2_CORPUS_SSOT_2026_08.md). Формула стадии: [`../../docs/demo/KT2_JURY_FAQ_2026_08_12.md`](../../docs/demo/KT2_JURY_FAQ_2026_08_12.md).

## Слайд 1. Проблема

- Комплект проектной документации расходится сам с собой: ведомость, модель и чертёж по отдельности «чистые».
- Дефект живёт между файлами и обычно всплывает уже на площадке.
- Ручная сверка зависит от квалификации и времени эксперта; пропуск стоит дороже, чем находка.

## Слайд 2. Решение

- AeroBIM — ассистент приёмки комплекта, не замена эксперта и не среда общих данных.
- Вход: IFC, IDS, чертежи, тексты спецификаций и расчётов.
- Выход: находка с GUID, правилом, парой expected/observed и ссылками на доказательства (HTML, JSON, BCF).
- Вердикт остаётся за человеком. Система не подписывает переход Shared → Published.

## Слайд 3. Архитектура

- Четыре контура: загрузка → детерминированная проверка → советующий ИИ → отчёт.
- Технический флаг `summary.passed` ставят только детерминированные движки (ADR-001).
- Языковая или визуальная модель не может превратить отказ в успех.
- Молчание не считается успехом: пропуск обязательной проверки роняет комплект.

## Слайд 4. Демонстрация

- Команда в терминале на учебном комплекте: `python -m aerobim.tools.run_demo_ifc_acceptance_gate`.
- IFC + IDS → находка с GUID элемента, идентификатором правила, expected/observed.
- Наложение проблемной зоны на PDF — детерминированные рамки, не компьютерное зрение.
- `summary.passed=false` на демо-пакете ожидаем: в учебном комплекте заложены дефекты.

## Слайд 5. Методика

- Протокол измерения качества опубликован **до** данных заказчика.
- Целевые цифры ТЗ — критерии оценки заказчика, не наши замеры.
- Разметка TP/FP, согласие экспертов и программа измерения готовы; без корпуса заказчика оценку продукта не публикуем.
- Открытые бенчмарки — регрессия движка, не корпус «Самолёта».
